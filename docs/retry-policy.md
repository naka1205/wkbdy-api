# 重试与关联 ID

面向客户端的重试契约：哪些失败可以重试、要等多久、以及如何把客户端的一次任务与我们和上游的日志对齐。策略参考同系列的 `autoclaw-api/docs/retry-policy.md`，本文只描述本网关实际实现的行为。

## 失败分类与重试

| 情况                             | 客户端响应                                                             | 账号池处理                                                     |
| -------------------------------- | ---------------------------------------------------------------------- | -------------------------------------------------------------- |
| 成功                             | 200                                                                    | 保留占号绑定，连续失败计数清零                                 |
| Key 无效、参数错误、模型不存在   | 原有 401 / 400 / 404                                                   | 不触碰上游账号                                                 |
| 上游 5xx、连接失败、SSE 解析失败 | 429 + `Retry-After`（上游未给出时默认 1 秒）                           | 前 3 次只计数；第 3 次起按 `pool.cooldownSeconds` 指数退避暂停 |
| 上游超时                         | 429 `upstream_timeout` + `Retry-After`                                 | 同上                                                           |
| 普通上游限流（429）              | 429 `rate_limit_exceeded` + `Retry-After`                              | 同上                                                           |
| 明确额度/余额不足                | 先自动换号重试；池内无可用账号时回 429 `insufficient_quota`            | 按 `pool.quotaRetrySeconds` 暂停（不记失败次数），到期自动探测 |
| 账号令牌被上游拒绝（401/403）    | 先自动换号重试；池内无可用账号时回 429 `upstream_authentication_error` | 立即暂停；`oauth` 账号先刷新同一账号重试一次                   |
| 上游封控该账号（如 `410004`）    | 先自动换号重试；池内无可用账号时回 429 `upstream_error`                | **直接停用该账号**，需在面板重新启用；占号立即释放             |
| 上游 4xx 且属于请求本身问题      | 400 `invalid_request`（原样透出上游消息）                              | 与账号无关，不暂停                                             |
| 账号已暂停，池中还有别的账号     | 正常请求 → 使用其他账号                                                | 占号按可用账号重新分配                                         |
| 池中没有任何可用账号             | 503 `upstream_error` + `Retry-After`                                   | 不抢占其他 Key 的占号；`Retry-After` 取最近一次冷却剩余秒数    |
| 客户端主动断开                   | 499                                                                    | 不计失败                                                       |

要点：

- **暂停原因是独立字段**，面板与日志都能区分：`cooldown_reason` 取 `quota`（额度耗尽）、`transient`（上游 5xx / 连接失败 / 普通 429 限流 / 超时）、`auth`（令牌被拒需重新登录）、`blocked`（上游封控已停用）。同一张表还记录 `quota_retry_after`（探测时间）与 `quota_scope`（`credits` 只挡计费模型，`account` 所有模型都挡）。
- 额度耗尽**不记失败次数、不进入指数退避**，因为它不是坏账号：只按 `quota_retry_after` 暂停，到期后放行探测；任意一次成功请求或面板重新启用都会清除 `quota_exhausted_at` / `cooldown_reason`。上游对免费（`x0.00`）模型同样会回 `14018 Credits exhausted`，这种情况下 `quota_scope` 记为 `account`，等充值后统一恢复。
- 普通限流与负载（上游 429 但没有额度字样）走 `transient`：先只计数，连续 3 次才按指数退避暂停，避免把一次上游抖动当成账号故障。
- 封控（`410004` / 「账号已被封控」等消息）不做冷却重试，而是把账号 `enabled` 置 0，避免反复撞墙。
- **账号级失败会在同一次客户端请求内换号重试**（额度耗尽、令牌被拒、账号被封，最多 3 个账号）：客户端不会因为池里某一个账号没额度就中断整个任务。只有池内没有可用账号时，失败才会回给客户端，且此时回的是第一个失败账号的错误（例如 `insufficient_quota`），不是笼统的「无可用账号」。
- 可重试的错误体同时带 `error.retryable: true` 与 `error.retry_after`，响应头带 `Retry-After`；`/v1/chat/completions` 与 `/v1/responses` 行为一致（流式提交后的错误帧同样带这两个字段）。
- 上游 `Retry-After` 会被解析（秒数或 HTTP 日期，上限 86400 秒）并原样回传；错误体同时带 `error.retry_after`。上游没给时，可重试的失败默认给 1 秒，避免客户端立刻打回。
- 只有可重试的失败使用 429；参数、模型、鉴权等客户端错误保持 4xx，不会被误判为上游故障。
- 临时失败（5xx / 429 / 网络 / 协议解析）连续 3 次才暂停账号：单次抖动不会让一个长任务换号；连续失败说明该账号确实不可用，第 3 次起暂停并释放绑定，重试即可换到其他账号。
- 暂停时长复用账号隔离的指数退避：`pool.cooldownSeconds × 2^(n-1)`，上限 30 分钟；任意一次成功请求清零。

### 客户端建议

1. 4xx（除 429）不要重试：改请求参数或模型。
2. 429 / 503 按 `Retry-After`（或 `error.retry_after`）等待后重试；同一 Key 重试可能落到同一账号，也可能因暂停换到别的账号，因此每次请求都要带完整上下文。
3. 重试时保持 `X-Task-Id` / `X-Session-Id` / `X-Zcode-Trace-Id` 不变，用 `X-Logical-Request-Id` 标记「同一次模型调用的重试」，`X-Retry-Attempt` 记录第几次，便于按任务聚合日志。

## 关联 ID

客户端可以带上这些头，用于把自己的任务、我们收到的请求和上游的调用串起来。值只能是长度 ≤128 的字母、数字、`_ . : -`，不能是凭证；不符合要求返回 400 `invalid_correlation_id`。

| 请求头                             | 用途                                              |
| ---------------------------------- | ------------------------------------------------- |
| `X-Task-Id`，缺失时用 `X-Query-Id` | 任务关联；一个任务可以包含多次模型调用            |
| `X-Session-Id`                     | 会话 ID                                           |
| `X-Zcode-Trace-Id`                 | 客户端追踪 ID                                     |
| `X-Request-Id`                     | 记为客户端请求 ID；**不会**覆盖网关自己的请求 ID  |
| `X-Logical-Request-Id`             | 同一次模型调用的多次重试共享；缺失时取网关请求 ID |
| `X-Retry-Attempt`                  | 客户端尝试序号，1–10000                           |

网关回传：

- `X-Request-Id`：网关请求 ID，等于日志里的 `request_id`；所有响应都带（含 4xx/5xx 与流式响应）。
- `X-Logical-Request-Id`：本次逻辑调用的关联 ID。
- `X-Task-Id`：客户端提供时原样回传。

上游侧：网关把 `X-Logical-Request-Id` 作为 `X-Request-ID` 发给 WorkBuddy 上游，上游在响应头 `x-request-id`（以及错误体 `requestId`）回显该值，所以一次调用在两侧是同一条 trace；上游回显值记入日志的 `upstream_request_id`，向上游报障时可直接引用。

关联 ID 只用于诊断：网关不做请求去重、不提供幂等重放保证；同一个任务 ID 下的多次调用互相独立。

## 日志与管理端

每条请求日志记录 `task_id`、`session_id`、`trace_id`、`client_request_id`、`logical_request_id`、`client_attempt`、`upstream_request_id` 与 `credits`（上游计费值）。管理端「请求日志」页可以按任务 / 逻辑请求 ID 过滤（可同时按客户端密钥筛选），详情弹窗展示全部关联字段。

## 已知差距

与 `autoclaw-api` 的策略相比，本网关暂未实现：

- 独立的 30 秒 / 600 秒两档暂停策略（我们用同一个指数退避，阈值为 3 次而非 6 次）。
- 额度耗尽的持久标记（按暂停处理，冷却到期后会再次尝试）——`autoclaw-api` 会一直排除到恢复为止。
- 模型级别的暂停与恢复探测（上游某个模型整体故障时，目前只会逐个暂停账号）。
- 建连阶段的额外一次重试（目前只有 401 刷新后的重试）；本网关额外做了账号级失败的同请求换号，`autoclaw-api` 是在下一次客户端请求才换号。
